On a failed gate, leave the last known-good published image serving.

Sync submodules only to the recorded pins in the newly restacked superproject; preserve any existing dirty submodule instead of overwriting it. Do not resolve conflicts or migration/product ambiguities automatically. No force-push, deletion, reset, clean, or unrelated history rewrite is authorized.

## Exclusive lock wrapper (Bash example)

Run the whole maintenance job through one lock owner. Atomic `mkdir` admits one invocation; **any existing lock fails closed**, including an apparently dead owner. Automatic stale-lock reclamation can race with a new owner, so an operator must verify and quarantine stale locks between runs. Configure `LOCK_DIR` on a protected local filesystem shared by scheduled invocations, not a network filesystem with uncertain `mkdir` semantics.

```bash
#!/usr/bin/env bash
set -euo pipefail
umask 077

LOCK_DIR="${HERMES_MAINTENANCE_LOCK_DIR:?set an absolute local lock path}"
HOST="$(scutil --get LocalHostName)"
mkdir -p "$(dirname "$LOCK_DIR")"

if ! mkdir "$LOCK_DIR" 2>/dev/null; then
  echo "Maintenance lock already exists; refusing: $LOCK_DIR" >&2
  exit 73
fi

printf '%s %s\n' "$HOST" "$$" > "$LOCK_DIR/owner.tmp"
mv "$LOCK_DIR/owner.tmp" "$LOCK_DIR/owner"
cleanup() { rm -f "$LOCK_DIR/owner"; rmdir "$LOCK_DIR" 2>/dev/null || true; }
trap cleanup EXIT HUP INT TERM

cd "${WITCHHUNT_READER_REPO:?set repository path}"
trap 'exit 129' HUP
trap 'exit 130' INT
trap 'exit 143' TERM
"${HERMES_DAILY_JOB:?set exact maintenance command}"
```

Operational caveat: a killed process can leave a stale lock. Inspect its owner record and run log, verify the process identity and that no invocation is running, then quarantine it manually before scheduling another run. Never add age-only or automatic stale-lock reclamation. The final command must be the configured local job entry point; do not put a guessed Hermes invocation here. All scheduled invocations must use this same wrapper and lock path. The job runs as a child so the wrapper's `EXIT` trap releases the lock after completion.

## Daily sequence

1. **Fetch and pin upstream.** Capture the old `upstream/master` tip, fetch only `upstream`, and resolve the new tip to a full immutable SHA. A new upstream tip is an expected daily input, not a reason to stop. Verify existing local metadata heads, base ancestry, backup refs, and worktree safety before restacking. Stop if membership or ancestry is ambiguous.
2. **Restack the approved local stack.** Calculate and record each exact old base, old head, and new parent from metadata order. Back up all tips and raw metadata first. Rebase the first topic onto the pinned upstream SHA, then each topic onto its already-restacked predecessor using its captured old base; never sort by number or infer a local trunk from a remote-qualified name. Rebase only the intended branches; leave local `master` and remote tips unchanged. Update metadata heads and bases to the verified resulting refs. On a conflict, leave the backed-up operation available for human review and stop; do not automatically reset, discard, or resolve it. Never force-push.
3. **Gate cleanliness again.** Confirm no unexpected worktree or submodule changes, no non-exempt untracked paths, and no affected unrelated worktree. Preserve the `docs/superpowers/` exception without staging it. Record final resolved source commit and active metadata order.
4. **Provenance and duplicate guard.** Compare full source commit, upstream SHA, submodule pins, build environment/version and configuration hash with the last successful immutable manifest **before testing or building**. If the inputs match and served acquisition readback still matches its recorded artifact SHA-256, record `unchanged` and skip rebuilding/republishing. Otherwise continue. Branch name alone is not identity. The same inputs yielding different artifact hashes require nondeterminism review. Keep manifests and command/tool/test/readback evidence outside disposable build output.
5. **Run tests RED/GREEN.** For a new behavioral adaptation, first prove a targeted regression fails against the original implementation, then passes with the fix; never fabricate RED evidence or mutate the live checkout while another build is running. An unchanged implementation needs the existing regression suite, not an artificial daily RED. Run `cmake -S test -B .pio/host-tests`, `cmake --build .pio/host-tests -j 8`, and `ctest --test-dir .pio/host-tests --output-on-failure -j 8`. Any failure stops publication.
6. **Build explicitly.** Run `pio run -e x4pro_gh_release -e gh_release` from the repository root. Record compiler/PlatformIO versions, explicit build variables, source/submodule commits, environments, compiled versions, commands and exit statuses. Use only reviewed required environment variables; do not expose secrets in provenance. Derive each output path from the configured build directory and observed successful output. Publish only the X4 Pro artifact; the C3 build is a portability gate. Do not upload to a device.
7. **Smoke-check before publication.** Run `/Users/traceywooden/.platformio/penv/bin/python /Users/traceywooden/.platformio/packages/tool-esptoolpy/esptool.py image-info .pio/build/x4pro_gh_release/firmware.bin`; this installed runtime was verified with esptool 5.3.0. Require ESP32-S3, valid checksum/validation hash and the expected DIO/16 MB image configuration. Verify SHA-256 and byte size separately. The image's SDK application descriptor is not the reader source revision: record the clean Git SHA and explicit compiled version in provenance and catalog, not that descriptor's SDK version. Device acceptance remains unverified.
8. **Immutable publish, preserve rollback.** Create a new per-revision staging directory under `.pio/opds-firmware/`; never overwrite an existing historical image or launcher. Copy the validated artifact to a temporary file on that filesystem, verify its hash, and atomically rename it to its new final filename. Derive the next catalog launcher from the positively identified live launcher: preserve every existing artifact entry unchanged and append the new image with its full source SHA in the version/provenance. Preserve the old launcher and artifact checksums for rollback. Never point a catalog at a temporary or partially written file.
9. **Replace only the proven service target.** Re-discover PID, executable, full command line, cwd, listening address/port, and served artifact. Confirm they match the deployment's exact managed service definition and target. Do not kill PID `53583` just because it was observed previously; do not stop another process sharing the port. If the service is not demonstrably the intended process, stop and ask the deployment owner. Launch/restart using the owner-supplied exact launcher and values; verify it is listening and its process reports the intended artifact hash/size. Never expose a newly bound wildcard interface unless the established firewall/Tailscale ACL provides the documented boundary.
10. **Read back over the actual client route.** Fetch the established OPDS URL, verify HTTP success, board/version/full source revision and artifact SHA-256, then download its acquisition link and verify vendor MIME type, byte size and SHA-256 against the local staged artifact. Verify all prior entries still resolve. Record responses without credentials. If cutover readback fails, stop only the positively identified new server, relaunch the preserved previous catalog launcher, prove its feed/download hashes, then report failure. Do not overwrite any artifact to roll back.
11. **Close the run.** Write the immutable manifest outcome (success, unchanged, or failure), source/test/build provenance, artifact hashes, service identity, URL-readback evidence, and explicit `device acceptance: unverified`. Release the lock on clean exit. Do not commit or push as part of the scheduled task.
